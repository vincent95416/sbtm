# 探索性測試

## 0. 確認輸入（缺一不可）
開始前檢查以下資訊是否齊全，缺少的逐項詢問使用者，全部確認前不得開始：
- 需求原文（不接受口頭摘要；若使用者只給摘要，請他提供原文或 ticket 連結）
- 角色
- 環境與版本：先依 CLAUDE.md「版本與環境取得」的方式自取，取得不到才列為缺項詢問
- 可用的測試資料
- 不測試的範圍

## 1. 理解輸入
- 讀取使用者提供的需求、spec 或 test case
- 拆解出具體要驗證的點；不清楚的地方列為「待確認問題」，不要自行假設
- 若某個驗證點因規格不清楚而無法進行，在產生 charter 前先詢問使用者

## 2. 定位
- 讀取範圍依 CLAUDE.md 共通規則 #10
- 列出可能受影響的周邊區域
- 地圖中沒有的頁面，記入報告的「建議的地圖修正」

## 3. Charter
- 依格式產生 charter（驗證點、進入點、周邊影響、需要的資料、可能的不可逆操作、步數上限）
- **交給使用者確認後才開始探索**

## 4. 探索
- 先走通正常路徑，再依啟發法嘗試邊界與異常
- 在以下時機截圖，保存到 records/artifacts/：每個 checkpoint、發現差異時、執行需詢問操作的前後
- 遇到 CLAUDE.md「需先詢問 QA 的操作」：依 CLAUDE.md 的詢問協定處理
- 遇到 CLAUDE.md「禁止事項」：不執行、不詢問，記錄到「未能測試」並附理由
- 達到步數上限即停止，未完成的部分記錄到「未能測試」

## 5. Checkpoint 時機
依 CLAUDE.md 的 checkpoint 格式回報。觸發時機與預設行為：

| 時機 | 預設 |
|---|---|
| 完成一個 charter 驗證點 | 不需介入就繼續 |
| 步數或時間過半 | 不需介入就繼續 |
| 發現差異，在深追之前 | 需裁決才能繼續 |
| 發現非 charter 範圍的現象，在偏離之前 | 需裁決才能繼續 |
| 要套破壞性啟發法（換角色重現、重開瀏覽器、大量輸入）之前 | 需裁決才能繼續 |
| 被阻塞（缺資料、charter 模稜兩可、頁面行為不符預期） | 需裁決才能繼續 |

所有 checkpoint 內容最後彙整到報告對應段落。

## 6. 報告
- 依本檔「格式」段落寫入 records/YYYY-MM-DD-<topic>.md
- 差異只列「可能原因」，「判定」欄位留空給 QA
- 涉及資料驅動內容的差異，把「環境資料」列為第一個可能原因
- 規格與實作不一致：不修改任何規格文件，寫進「差異」與「待確認問題」
- 地圖與實機不一致：寫進「建議的地圖修正」，只包含導航資訊

## 探索啟發法
- 正常路徑先走通，再嘗試邊界與異常
- 邊界值、空值、超長輸入、特殊字元
- 重複操作、快速連續點擊、上一頁後再操作、重新整理
- 換角色、未登入狀態直接進入網址
- 同一筆資料在不同頁面顯示是否一致（金額、數量、狀態）
- 觀察 console 錯誤與失敗的網路請求

## 格式

### Charter

````markdown
## Charter
- 輸入來源：<ticket 編號或文件名稱>
- 要驗證的點：
  1. <驗證點>
- 進入點：<路徑>（<角色>）
- 周邊影響：<頁面或功能>
- 需要的資料：<測試資料>
- 可能的需詢問操作：<動作>
- 不測試：<範圍>
- 步數上限：<數字>
````

## Charter
（貼上確認後的 charter）

## 符合
- 驗證點 <n>：<觀察>

### D<n> <標題>

- 證據：<截圖路徑>

|---|---|---|---|
