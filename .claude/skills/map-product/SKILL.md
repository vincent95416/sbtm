# 建立 / 更新產品地圖

## 開始前
1. 確認本次要處理的模組與角色；使用者沒說明就先詢問
2. 讀取 docs/product-map.md 與該模組現有的 features/ 檔案，不要讀取其他模組的檔案
3. 依 CLAUDE.md 的方式取得環境與版本

## 探索
- 一次只處理一個模組；單次最多 20 個頁面，超過時停止，回報已完成與剩餘的部分
- 使用本次指定角色的測試帳號登入後再開始
- 從模組入口開始，記錄每個頁面的：路徑、入口、主要操作、去向、可見角色
- 會送出資料的操作：只記錄「有送出動作，推測會做什麼」，不實際執行
- 遇到需要操作 confirm / modal 才能繼續：依 CLAUDE.md「需先詢問 QA 的操作」處理
- 超出本次角色權限、或需要特定資料才能進入的頁面：記錄到「未探索」並寫明原因，不要猜測內容
- 已有內容的頁面：逐項比對實機
- 內容邊界依 CLAUDE.md 共通規則 #8
- 不記 CSS / 實作細節（例如 cursor、class、selector）；只記畫面上看得見的、可操作的、有去向的

## 寫入
- 一律依本檔「格式」段落寫入；既有檔案格式不符時，一併修正為本格式
- 新增頁面檔前，先在索引中確認沒有相同頁面的檔案
- 新模組建立 features/<module>/ 目錄，並在索引新增一行
- 狀態與證據（僅操作表）：
  - 新增項目：標為「待確認」，附上證據（格式：環境 / 版本 / 角色 / 日期）
  - 既有項目證據欄以「人補 / 」開頭：不覆蓋、不改狀態；若實機與該條不一致，記入結束輸出「與人工補充不一致」清單讓 QA 裁決
  - 既有項目與實機一致：保留原狀態，以新證據取代舊證據
  - 既有項目與實機不一致：修改內容，狀態改為「待確認」，以新證據取代舊證據
- 相關網路請求、資料驅動內容（條列段）：
  - 既有條列含「［人補 / 」尾綴：不覆蓋；若實機與該條不一致，記入結束輸出「與人工補充不一致」清單讓 QA 裁決
  - 其餘既有條列：依既有探索規則就地更新
  - AI 新增的條列不加任何尾綴
- 修改既有內容時就地修正，不另開新檔
- 證據只保留最新一筆（僅操作表）；格式：AI 寫入「環境 / 版本 / 角色 / 日期」、annotate-map 寫入「人補 / 日期」。條列段無證據欄，annotate-map 以尾綴「［人補 / 日期］」標記
- 模組段每個模組一行；索引總行數上限依 CLAUDE.md 共通規則 #7
- 頁面檔達到 CLAUDE.md 共通規則 #7 的上限時，提出拆分方案並詢問使用者，確認後才拆分
- 「項目」「狀態」「證據」欄不得寫入帳號、密碼、個資或任何測試憑證；需要引用時指向 CLAUDE.md 說明的位置

## Checkpoint 時機
依 CLAUDE.md 的 checkpoint 格式回報。觸發時機與預設行為：

| 時機 | 預設 |
|---|---|
| 完成一個頁面的記錄 | 不需介入就繼續 |
| 走到 10 頁（過半） | 不需介入就繼續 |
| 既有地圖與實機不一致，在修改前 | 需裁決才能繼續 |
| 超出本次角色權限、無法進入 | 不需介入就繼續（記到「未探索」） |
| 遇到會送出資料的操作 | 走詢問協定，不走 checkpoint |
| 達到 20 頁上限或步數上限 | 需裁決才能繼續（問要不要拆下一次） |

## 結束時輸出
- 新增了哪些頁面
- 修改了哪些內容（修改前 → 修改後）
- 與人工補充不一致：<檔案 / 項目 / 現有「人補」條目 / 實機觀察>（供 QA 裁決）
- 不確定的地方
- 未探索的地方與原因
- 本次未完成、下次應繼續的部分

## 格式

### docs/product-map.md

```markdown
# Product Map

> 此檔為索引。所有 AI 自動寫入的內容標為「待確認」，由 QA 審核後改為「已確認」。

## 模組
| 模組 | 入口 | 主要頁面 | 角色 | 細節 | 狀態 |
|---|---|---|---|---|---|
| 結帳 | /cart | 購物車、付款、完成頁 | member | [checkout](features/checkout/) | 待確認 |

## 主要流程
- <流程名>：<頁面 A> → <頁面 B> → <頁面 C>

## 未探索
| 位置 | 原因 |
|---|---|
| /admin/** | 缺少 admin 帳號 |

## 資料驅動內容
- <項目>（<觀察到的值與可能來源>）
```

### docs/features/<module>/<page>.md

```markdown
# <頁面名稱>
- 路徑：/checkout/:id/payment
- 入口：購物車頁「前往結帳」
- 角色：member（guest 會被導向登入頁）

## 操作
| 項目 | 類型 | 去向 | 狀態 | 證據 |
|---|---|---|---|---|
| 前往付款 | 送出動作（未執行） | 完成頁（推測） | 待確認 | staging / a1f3c9e / member / 2026-10-05 |
| 返回購物車 | 連結 | 購物車頁 | 已確認 | staging / a1f3c9e / member / 2026-10-05 |
| 優惠碼 | 輸入 | — | 待確認 | 同上 |
| 版本字串 | 顯示 | — | 已確認 | 同上 |

## 相關網路請求
- 載入時：`POST /api/order/:id` → 200（取得訂單資料）
- 操作觸發：`POST /api/payment/apply`（「前往付款」送出時；未實際觸發）

## 資料驅動內容
- 付款條款文案
```

規則：
- 「類型」只能是：連結 / 按鈕 / 輸入 / 顯示 / 送出動作（未執行） / 送出動作（已執行）
  - 輸入：textbox、textarea、checkbox、radio、select 等表單控件
  - 顯示：版本字串、靜態文字、圖片、影片等無互動元素
  - 其餘字面意思
- 「狀態」欄只能填：待確認 / 已確認
  - 不要填值、預設行為、啟用性、UI 文字等其他資訊
  - 控件的預設值、預設勾選狀態、是否啟用等觀察，若要記錄，寫在「項目」描述中（例如「儲存帳號 checkbox（預設勾選）」），而非狀態欄
- 「去向」為推測時，必須加註「（推測）」；無去向填「—」
- 「相關網路請求」段落：
  - 格式：`<時機>：<METHOD> <URL> → <status>（<說明>）`
  - 時機只能是：載入時 / 操作觸發 / 定時 / 其他
  - 只記功能性請求（API、媒體、關鍵第三方）；js / css / font / 分析工具省略
  - 外部網域加註「第三方」或「CDN」
  - 未實際觸發的請求標「（未實際觸發）」
- 「主要流程」段（僅 docs/product-map.md）：
  - 只寫跨頁面的導航鏈：`<流程名>：<頁面 A> → <頁面 B> → <頁面 C>`
  - 不寫 API、欄位、業務規則；頁面內的 API 歸頁面檔的「相關網路請求」
  - 只列完整走過的流程；單一頁面不列
- 「資料驅動內容」段：
  - 全站共用的項目（例如代理商 avatar、多語下拉清單）放 docs/product-map.md 的同名段落
  - 僅此頁出現的項目（例如登入頁的背景影片）才放在頁面檔
  - 寫入新頁面時先掃一遍 index 的清單，避免重複
- 不要新增其他段落
