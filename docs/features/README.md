# docs/features/

> 各模組 / 功能的細節文件。由 `map-product` skill 自動建立並由 QA 審核。

## 目錄規則
- 一個模組一個子目錄：`docs/features/<module>/`
- 每個 feature 一個檔：`docs/features/<module>/<feature>.md`
- 檔名用 kebab-case（例：`checkout/payment.md`、`member/profile.md`）

## 檔案範本
以 `map-product/SKILL.md` 的「格式」段落為準，不要在此另立一份。範本摘要：

```markdown
# <頁面名稱>
- 路徑：<URL pattern>
- 入口：<從哪裡進來>
- 角色：<可見此頁的角色；其他角色的行為>

## 操作
| 項目 | 類型 | 去向 | 狀態 | 證據 |
|---|---|---|---|---|

## 相關網路請求
- <時機>：<METHOD> <URL> → <status>（<說明>）

## 資料驅動內容
- <來自 CMS 或測試資料的欄位；不一致時優先懷疑環境資料>
```

格式規則（詳見 `map-product/SKILL.md`）：
- 「類型」只能是：連結 / 按鈕 / 輸入 / 顯示 / 送出動作（未執行） / 送出動作（已執行）
- 「去向」為推測時，必須加註「（推測）」；無去向填「—」
- 「相關網路請求」只記功能性請求，時機限：載入時 / 操作觸發 / 定時 / 其他
- 不要新增其他段落（例：已知未探索、修改紀錄）；證據只保留最新一筆，歷史由 git 保存

## 原則
1. **顆粒度是「頁面與流程」**，只記錄導航資訊，不記錄業務規則、欄位驗證、計算邏輯。
2. **送出類操作只記錄「會做什麼」，不實際執行。**
3. **AI 新增或修改的內容一律標為「待確認」**，由 QA 改為「已確認」。
4. **單檔超過 300 行時拆分**，原檔只留摘要與連結。
