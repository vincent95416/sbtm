# 討論筆記：review 流程設計疑慮

- 日期：2026-10-16
- 類型：流程設計討論（非探索報告，非地圖）
- 狀態：**暫存，待下次回顧後決定方向**
- 相關檔案：CLAUDE.md 共通規則 #4、#8；`.claude/skills/map-product/SKILL.md`

---

## 原始疑問（by QA）

> review 的動作都是去找到待確認 > 已確認嗎？這樣好像跟原本工具想要的方向有點背道而馳，而且未接觸過的同仁還可能會把他已知的事情直接改寫 md 檔，造成探索混亂等等。

---

## 問題拆解

### 1. 「review = 待確認 → 已確認」淪為背書

目前流程預設：
```
AI 寫入「待確認」→ QA 看 → 改成「已確認」
```

隱性假設都站不住腳：

| 假設 | 實際上 |
|---|---|
| QA 真的會逐條驗證 | 20 條「待確認」整批打勾（確認偏誤 + 審美疲勞） |
| QA 的角色是「驗證 AI」 | QA 本身是**產品知識持有者**，不只是驗證者 |
| AI 不會寫錯 | AI 會誤判，但 skill 格式沒有「否決」「存疑」「人工補充」語義 |

### 2. 未接觸同仁想直接改 docs 的誘惑

情境：新 QA 加入 → 他知道「個人設置裡的『限紅返水』是會員 VIP 等級設定」→ 看到 docs 標「未探索」→ 自然反應是**直接編輯 md 檔**。

但 CLAUDE.md 共通規則 #4「docs/ 只能透過 map-product 修改」導致：

- 同仁的既有知識**沒有合法入口**進入 docs
- 遵守規則 → 得跑 map-product 問 AI 幫忙，很笨
- 不遵守規則 → AI 下輪 map-product 時「發現不一致」會覆蓋人寫的

**無論走哪條都卡**。

---

## 建議改善方案（4 個方向，可組合）

### 方向 A：擴大「狀態」欄的語義

從只有「待確認 / 已確認」，變成：

| 狀態 | 意義 | 誰寫 |
|---|---|---|
| 待確認 | AI 剛寫入，未驗證 | AI |
| 已確認 | 已驗證對 | 人 |
| 否決 | AI 寫錯，實際上不是這樣 | 人 |
| 人工補充 | 不是 AI 探索到的，是人直接寫的 | 人 |
| 存疑 | 人看了也不確定 | 人 |

**解決**：「否決」和「人工補充」有地方放。
**沒解決**：「人直接改 docs」的流程問題。

### 方向 B：讓人也走 skill（新增 `annotate-map`）

新 skill 專門給人用：
- 讓人加「人工補充」條目（自動標上作者、日期）
- 讓人把 AI 的條目「否決」「補充」「修改」
- 走這 skill 就有 trace，不會亂改

**人的入口變成**：
```
我知道這個功能怎樣 → /annotate-map 補到 docs/
```

**解決**：給人一條合法的 docs 寫入路徑；避免「直接改 md 檔」的衝動。

### 方向 C：區分「探索結果」vs「規格知識」

目前 docs/ 混了兩種：
- **探索結果**：AI 走過 UI 看到的（會動態變）
- **規格知識**：人本來就知道的業務邏輯（相對穩定）

分成兩個檔案或兩個段落：
- `docs/features/<module>/<feature>.md` → 導航結構（AI 寫 / 人 review）
- `docs/features/<module>/<feature>.rules.md` → 業務規則（人寫 / AI 讀但不改）

**衝突**：跟 CLAUDE.md 共通規則 #8「地圖只記導航資訊，不記業務規則」直接衝突，得先決定業務規則要不要納入 docs/、放哪、誰寫、怎麼跟地圖連結。

### 方向 D：改 review 流程，讓它更像 PR review

Review 不是「改 md」，而是「每個待確認項目**附上一條回應**」：
- 「確認：10/16 QA Vincent 驗過」
- 「否決：這條其實是 X，不是 Y」
- 「補充：這頁還有個 Z，AI 沒看到」

QA 的動作是**留痕**，不是改內容。改內容仍走 map-product。

**要有工具支援**：commit message / 外部表格 / 專門的 review 欄位，有點重。

## 後續結論（2026-10-27 ~ 2026-10-30 多輪討論落檔）

本筆記寫於 2026-10-16。後續在 2026-10-27、2026-10-30 兩輪討論中逐一處理，決議如下。原方案 A/B/C/D **全數不採用**，走了另一條路線 —— 核心是**重新定義「狀態」與「review」的語義**，而不是在原本框架內調整。

### 1. 核心觀念重構：「待確認」是永久屬性，不是待辦清單

這是整個新設計的基石：

- 狀態欄只有「待確認」一值 —— 「AI 寫的、未經人改」的**永久屬性**
- 不設「已確認」（完全移除，不是改名）
- 「人經手」痕跡**不在狀態欄**，而在：
  - 操作表的**證據欄**：`人補 / <日期>`
  - 條列段 / header 角色欄的**行尾尾綴**：`［人補 / <日期>］`
- 滿地圖的「待確認」是正常的，不是作業清單
- QA 想改內容的唯一入口：annotate-map

**為什麼這樣**：批量打勾本身不是驗證。承認後，「已確認」永遠是幻象。既然如此，就不留 batch-tick 的誘惑，哪怕改名「✓」或改成刪字都一樣。

### 2. Review 的新實質：用的時候順手修

Review 不是儀式，是三個**被動觸發點**：

1. 讀地圖當 reference 時發現某條錯 → `/annotate-map` 改那一條
2. map-product 跑完回報的「與人工補充不一致」/「可能與排除清單重疊」清單 → 針對那幾條走 annotate-map 處理
3. annotate-map 自己的 preview → QA 補 A 條目時順便看到同頁其他可能也不對的

reviewer 角色消失，取代為「地圖的使用者」。

### 3. docs/ 兩個合法入口（CLAUDE.md 共通規則 #4 改寫）

- AI 跑 Playwright 探索補 / 修 → `/map-product` skill
- QA 已知的產品知識補 / 修 / 刪 → `/annotate-map` skill
- **不直接編輯 md 檔**；手改沒「人補」標記，下輪 map-product 可能視情況覆蓋

### 4. Header 欄位的縫處理

- `角色` 納入 annotate-map 可修改範圍，用行尾 `［人補 / 日期］` 標記
- `路徑`、`入口` 由 map-product 探索專屬，annotate-map 不碰
- map-product 遇到 header 角色欄「人補」尾綴時不覆蓋，不一致時走「與人工補充不一致」清單

### 5. 刪除防重入：排除段落

要解決「annotate-map 刪了 → 下輪 map-product 跑實機又重新寫入」的 side effect：

- 原本考慮用 git log 查刪除歷史（討論中的方向 W），但 **docs/ 刻意不入 git**（framework public / data private 的架構，為了放公開 git 給人觀摩），所以 git-based 方案不可行
- 改走**檔內自我表達**的方向：
  - annotate-map 的刪除動作必問動機（Checkpoint 必裁決），依分類處理：
    - **A**（UI 真的沒）→ 直接刪
    - **B**（UI 有但不該在這頁）→ 搬到頁面檔底部「排除」段落
    - **C**（想換措辭）→ 建議改走「修改」動作
    - **D**（隱藏 / 灰度功能）→ 搬到「排除」段落
  - map-product 寫入前讀該頁的「排除」段落，用**語義判斷**同一 UI 元素，確定跳過 / 不確定記入裁決清單
  - map-product 不寫入「排除」段落（只讀）

### 6. 連帶的清理

- 移除所有「由 QA 審核」「QA 審核後改為已確認」字樣（CLAUDE.md、README×2、docs/product-map.md top note、docs/features/README.md）
- 兩個既有 feature 檔的 35 條既有「已確認」批次改為「待確認」（一次性遷移，不是週期性 ritual）
- `docs/features/games/lobby.md:34` 的狀態欄違規括號說明搬到項目欄
- `docs/features/games/lobby.md:27` 的主題切換 icon 由 QA 口述知識更新內容，證據欄標 `人補 / 2026-10-27`

### 8. 架構決定（影響日後所有設計）

**docs/ 不入 git 是刻意的**（framework public / data private）。這限制了所有「用 git log 偵測狀態變化」的方案，所有歷史與衝突處理都必須靠**檔內自我表達**。本輪的「排除」段落、「人補」尾綴、map-product 的「與人工補充不一致」清單，都是這個哲學的具體化。
